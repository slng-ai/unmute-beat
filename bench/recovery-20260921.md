# POC conversation recovery — 21 September 2026

Implemented on the implementation worktree based on `c6e8cfd`. The default
Gemini 3.5 arm passes all 24 targeted recovery scenarios (eight cases, three
repetitions). This is a text/runtime recovery result, **not POC closure** or a
measurement of voice quality.

## What caused the regression

- **Consent parsing rejected ordinary selections.** `01:00, please`, `1:00 PM`
  and `one, please` did not authorize the offered 13:00 slot. Minutes could
  also be discarded while parsing `10:30 AM`. The parser now preserves minutes
  and explicit AM/PM, resolves unqualified hours against offered slots, and
  refuses negative or alternative selections. Affirmative variants are still
  accepted only against the application-owned pending question.
- **Approval and the next question shared one expiring slot.** Complaint
  approval disappeared during phone verification. Accepted complaints now hold
  their exact summary, requested resolution and identity separately. The
  model-facing recording finisher takes no arguments: it records that stored
  payload once, instead of asking the model to reconstruct it. Corrections,
  abandonment and identity changes invalidate approval; write reconciliation
  and execution guards remain in place.
- **Complaint recording invited another model response.** The ordinary tool
  spoke a receipt and then the model generated another acknowledgement.
  Recording is now a terminal output tool with one grounded receipt and a
  pending-approval statement. The production schema demonstration was removed;
  the isolated schema-validation proof remains in `tests/test_state.py`.
- **Move routing could not perform the requested action.** The concierge was
  instructed to handle a move by reading the diary, but could not save it.
  The booking prompt also asked for confirmation despite “same time” selecting
  the existing time. Moves and cancellations now route directly to booking;
  an available same-time move needs no additional confirmation.
- **Queued accepted input could disappear.** Pipecat flushes queued context
  frames during interruption. Reading only the last user message subsequently
  lost a phone number already present in the aggregator's history. The adapter
  now reads every unseen user message. Cancellation carryover checks the current
  message occurrence, so an older identical “yes” cannot count as delivery of
  the new one. No interim transcription is promoted to accepted input.
- **“No thanks” was not a goodbye.** It can now close the call when answering
  an “anything else” question. Declining a redo or adding a new request does
  not close it.

Complaint prompts preserve acknowledgement, missing visit details and policy
before readback. Requested resolution is a required readback argument. A claim
that a complaint was recorded without a write is also withheld.

## Matched targeted results

The same `bench/recovery.py` was run in separate processes against archives of
`8570aa5`, `c6e8cfd`, and the repaired worktree, using the installed locked
runtime, Gemini 3.5, the same Monday clock and fresh fixtures. Main's application
code matches `8570aa5`; its later commits added documents. No branch was reset.

| `select_pm` | 3/3 | 0/3 | 3/3 | 3/3 |

These are regression-script outcomes, not population quality estimates. The
scripts check diary facts, single receipts, selected-time request counts and
hangup behavior. They do not automatically grade empathy or every policy
statement. Scripts can also become misaligned when an arm asks a different
question. Gemini 3.1 is reported separately; provider region is unpinned.
The retained runner headers captured defaults before fixture setup; the actual
per-scenario code resets the diary and pins the clock. Future headers now
explicitly report that fresh fixture and pinned clock, plus the suite digest.

## Runtime proof and checks

`tests/test_recovery.py` drives the actual Pipecat processor queue: a phone
context waits behind a blocked model run, an interruption flushes it, and the
next caller turn must retain the number. Restoring the old last-message-only
behavior produces the exact loss:

```
NEGATIVE CONTROL: old last-message-only path loses the phone: ['Sure', 'Sure Are you still with me?']
```

This proves a loss mechanism at the adapter seam. It does not establish that
all loss in the supplied recording originated there: raw caller audio and the
complete STT/endpointing event stream were not available for identical-audio
replay. A `TranscriptionFrame.finalized=False` is not by itself evidence that
its text was an interim hypothesis.

Retained [offline output](recovery-evidence/offline.txt),
[Ruff](recovery-evidence/ruff.txt), and [ty](recovery-evidence/ty.txt):

```
all 12 modules ok
All checks passed!
All checks passed!
```

Call settings are captured before the worker runs, with source/prompt/lock
fingerprints. Process configuration is cached rather than re-read when the call
ends. Call clock and starting fixture remain per-call values. Restart the bot
when changing code or prompts; startup metadata does not hot-reload code.

## Still open

- Gemini 3.1 sometimes asks for a complaint readback before receiving a requested
  resolution, then moves to verification without approval. Its final run missed
  one record. It also skipped empathy/policy in some verified-complaint runs and
  generated a redundant claim on a later yes; the guard withheld that claim.
  The 23/24 outcome score does **not** qualify this model for release.
- Identical-audio STT/endpointing replay, TTS playout and microphone/barge-in
  acceptance remain unmeasured. They require caller audio or a fresh recorded
  voice session. No matched voice-latency claim is made.
- Native Pipecat comparison remains blocked on an identified native build and
  matched configuration.

Run the explicit suite, not a label passed to the old scenario runner:

```bash
uv run --env-file .env python -m bench.recovery --repeats 3 --label recovery
BENCH_PINNED=1 uv run --env-file .env python -m bench.recovery --repeats 3 --label recovery-31
```

`--scenario` selects named cases explicitly and may be repeated. Every caller
turn and outcome is flushed to JSONL. The old completion ledger's claim that
these eight cases already existed has been corrected.
